GraceSoft DriveSync

Syncs Google Drive folders into a vector store for retrieval-augmented generation, and serves that index over REST and MCP. Multi-tenant by construction — every account gets its own API keys and its own isolated slice of the index.

Node 20+ TypeScript MIT Postgres · Redis · BullMQ

Overview

#overview

Paste a Drive folder ID, share it with a service account, and DriveSync keeps it in sync on a schedule: listing what changed, extracting text, chunking it, embedding it, and writing it into a vector store — ready to query over REST or hand to any MCP-compatible client.

  • Drive folder sync — folder access is verified before it's ever marked connected; a folder that's later unshared surfaces as NOT_ACCESSIBLE, not a silent stale success.
  • Extraction — Google Docs, Sheets, Slides, and PDFs with a text layer, to plain text.
  • Chunking — token-budgeted chunks with overlap, using the same tokenizer the reference embedding provider uses, so measured chunk sizes are the sizes that provider actually sees.
  • Pluggable providers — embeddings and vector storage are interfaces, not hardcoded SDK calls. OpenAI and Pinecone ship as the reference adapters.
  • Dedup & cleanup — a content-hash check skips re-embedding unchanged files; stale vectors are cleaned up when a file shrinks or disappears.
  • Retrieval with attribution — results carry chunk text and source (file, section), not just an ID and a score.
  • Observability — per-folder sync health and account-wide index totals, both scoped to the caller.

Quickstart

#quickstart

Requires Node 20+, a Postgres database, and a Redis instance. docker-compose.yml provides both locally.

git clone https://github.com/davinaleong/gracesoft-drivesync.git
cd gracesoft-drivesync
npm install
cp .env.example .env
# fill in .env — see Environment variables below
docker compose up -d
npm run prisma:migrate
npm run account:create -- "My Company"
npm run api-key:issue -- <accountId> "first key"   # prints the raw key once

Then, in separate terminals:

npm run dev      # REST API on PORT (default 3000)
npm run worker   # scheduled sync job
npm run mcp      # MCP server on MCP_SERVER_PORT (default 3001)

Share a real Drive folder with GOOGLE_SERVICE_ACCOUNT_EMAIL, then connect it:

curl -X POST http://localhost:3000/folders \
  -H "Authorization: Bearer <your-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"folderId": "<google-drive-folder-id>"}'

The worker picks it up on the next scheduled run (SYNC_CRON, every 15 minutes by default). Once synced:

curl -X POST http://localhost:3000/query \
  -H "Authorization: Bearer <your-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"query": "what does this folder say about pricing?"}'

Architecture

#architecture

Each stage below was built and unit-tested independently — several as pure functions, before the state they'd eventually consume existed at all.

Dedup & cleanup

Before re-embedding a changed file, its content is hashed; an unchanged hash skips straight to updating the tracked modifiedTime without touching the vector store. When a file is deleted or shrinks to fewer chunks than it had before, the trailing stale vector IDs are computed and removed — the shrink case is the one that's easy to miss if cleanup is only wired to full-delete events.

Design pattern used throughout

Nearly every external dependency here — Prisma, the Drive API, OpenAI, Pinecone, Redis — sits behind an interface with an injectable factory: create<Thing>(deps). Business logic is tested against fakes; only a thin wrapper around the real SDK ever touches a real network call.

Pluggable providers

#providers

EmbeddingProvider and VectorStore are interfaces the pipeline talks to — never a specific SDK directly. Two adapters ship as reference implementations.

EmbeddingProvider · attached

OpenAI

text-embedding-3-small by default (1536 dims). Batched, with retry/backoff on 429/5xx. Dimension is looked up from a fixed table — an unrecognized model fails at startup, not mid-sync.

VectorStore · attached

Pinecone

Per-account namespace, stable {fileId}-{chunkIndex} vector IDs. The index must already exist — this project never creates one for you.

Dimension compatibility — check before every deploy Embedding dimension is fixed per model and baked into a vector index at creation time. There is no partial or live migration between mismatched dimensions — assertEmbeddingDimensionMatchesVectorStore fails every sync run closed rather than writing wrong-dimension vectors. A real deployment hit this: text-embedding-3-small (1536 dims natively) configured against Pinecone indexes created at 512 dims. Every run failed correctly — but that also means zero syncing happens until the mismatch is fixed. Fix used here: set OPENAI_EMBEDDING_DIMENSIONS=512 to truncate the model's output to match the existing indexes, rather than recreating real infrastructure — verified end-to-end against the real OpenAI and Pinecone APIs.

Swapping either provider on a deployment with existing data always means a full resync — there's no in-place migration, by design. See Adding a provider for implementing a different one.

Multi-tenancy

#multitenancy

Every tenant is an Account, provisioned by an operator (npm run account:create) rather than self-service — this service shares one Google service-account identity across every tenant for Drive access, so an open signup endpoint would let anyone consume that shared quota.

An account authenticates with an API key (Authorization: Bearer dsk_...). The key resolves to an account, and every downstream operation is scoped to that account's ID. In the vector store, the account ID is the namespace — there is no shared namespace an account could accidentally read from or write into another tenant's data.

REST API

#rest-api

Every endpoint except GET /health requires Authorization: Bearer <api-key>. A missing, malformed, unknown, or revoked key all return the identical 401 {"error": "unauthorized"} — the response never signals why a key was rejected.

POST /query

Embeds the query, searches the caller's own account namespace, returns chunk text plus attribution.

{ "query": "what does this say about pricing?", "topK": 5 }  // topK optional, default 5, max 50

// Response
{
  "results": [
    { "text": "...", "score": 0.87, "fileId": "...", "fileName": "pricing.docx", "section": "Enterprise tier" }
  ]
}

Returns 200 either way — the verify request itself succeeded even when access was revoked:

// access revoked
{ "folder": { "...": "...", "status": "NOT_ACCESSIBLE" }, "error": "..." }

MCP tools

#mcp

Served over streamable HTTP at POST /mcp, stateless — no session state between calls. Authenticated the same way as REST: Authorization: Bearer <api-key> on the HTTP request, resolved by the identical requireApiKey middleware the REST API uses, not a parallel implementation.

ToolParametersReturns
search query (string, required)
topK (number, max 50, default 5)		 Same shape as /query's results, as JSON text
fetch_document fileId (string, required — from a prior search result) { fileId, fileName, text } — the reconstructed full document, or an isError result if not found or not the caller's

Deployment

#deployment

One Docker image, three independently-run processes — not three images. The current Dockerfile only defines a start command for the API server; the worker and MCP server run from the same image with an overridden command. Railway is the chosen host — one project, three services (api, worker, mcp) sharing this build, plus managed Postgres and Redis plugins.

ProcessEntry pointNeedsPublic?
API servernode dist/server.jsPostgres, Pinecone, OpenAIYes
Sync workernode dist/worker.jsPostgres, Redis, Drive, Pinecone, OpenAINo
MCP servernode dist/mcp.jsPostgres, Pinecone, OpenAIYes
 
npm run prisma:deploy   # `prisma migrate deploy` — apply pending migrations only, never generates one

Run once per deploy, before starting any process, against the target environment's real database. Never run prisma migrate dev against staging or production — it's a local-development command that assumes an ephemeral, disposable database.

Known gap — concurrent runs A single worker process never runs two jobs at once, and BullMQ's own per-job lock stops the same scheduled job being double-processed across multiple worker processes. There is no cross-process lock yet preventing two different jobs (a scheduled tick and a manual trigger, on separate processes) from processing the same folder concurrently. Run exactly one worker process until this is closed.

Full runbook — process topology, staging/production separation, post-deploy smoke test, rollback: deployment-runbook.md.

Contributing & adapters

#contributing

The main contribution surface this project is built around is a new EmbeddingProvider or VectorStore adapter:

  1. Implement the interface — see openaiEmbeddingProvider.ts / pineconeVectorStore.ts for the reference shape (an injected thin client wrapping the real SDK, with retry/batching logic around it).
  2. Run the shared contract test suite against your adapter (defineEmbeddingProviderContractTests / defineVectorStoreContractTests) — required, not optional, before a new-adapter PR merges. It's what catches an adapter that compiles but silently breaks a guarantee like namespace isolation.
  3. Register it in the config-driven factory — one case added to a switch, no plugin-loading machinery.

Full guide: adding-a-provider.md. Development setup and code-style conventions: CONTRIBUTING.md. Reporting a vulnerability: SECURITY.md.
