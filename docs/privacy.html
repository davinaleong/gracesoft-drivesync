Privacy Policy

Last updated 2026-08-10

This is a template describing what GraceSoft DriveSync — as self-hosted software — actually does with data today. It is not legal advice. If you operate a deployment of DriveSync for other people, have a lawyer review and adapt this (jurisdiction, data-retention periods, GDPR/CCPA or other regional obligations) before relying on it for a real business.

There is no central GraceSoft server

DriveSync is open-source, self-hosted software. Every deployment runs entirely on infrastructure its operator controls: their own Postgres database, their own Redis instance, their own Google Cloud service account, and their own OpenAI and Pinecone accounts. The people who maintain this open-source project never receive, store, or have access to any data processed by a deployment we don't personally operate ourselves.

Everything below describes what the software does with data when someone runs it — not a relationship between you and a company operating a shared service, because no such shared service exists.

What the software collects, per deployment

  • Account & API key data: an account name, and a hashed (HMAC-SHA256, never reversible) copy of each issued API key. A raw key is shown once at issuance and is never stored anywhere.
  • Drive file content: for every folder an account connects, metadata (file name, type, last-modified time) and extracted text content from Google Docs, Sheets, Slides, and PDFs in that folder.
  • Derived data: text chunks of that content, and the vector embeddings generated from them.

Third parties the software sends data to

Each of these is the operator's own account with that provider — the DriveSync project itself is never a party to this data flow, and never sees the data in transit.

  • Google Drive API — to list and read the contents of connected folders, using the operator's own Google Cloud service account.
  • OpenAI (or whichever EmbeddingProvider the operator configures) — extracted text is sent to generate embeddings.
  • Pinecone (or whichever VectorStore the operator configures) — chunk text, file metadata, and embeddings are stored here.

Your choices

  • Revoke folder access: unshare a connected folder from the service account's email in Google Drive. The next verification marks it inaccessible, and the software stops reading further content from it.
  • Revoke an API key: an operator can revoke any issued key at any time, immediately blocking further API or MCP access with that key.
  • Delete already-stored data: honestly — there is currently no built-in "disconnect and purge" action that removes a folder's already-indexed files, chunks, and vectors in one step. Unsharing stops future reads; previously indexed content remains in the operator's own Postgres database and vector store until removed directly. If you operate a deployment for other people, you're responsible for offering them a real deletion path — see the project's issues if you'd like to help build one.

Questions

This is an open-source project without a central support inbox. Open an issue on the GitHub repository with privacy questions about the software itself. If you're asking about a specific deployment, contact whoever operates it.
